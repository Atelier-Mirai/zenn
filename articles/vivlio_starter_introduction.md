## はじめに

「自分の本を作ってみたい」——そう思ったことはありませんか。

日々の仕事で培った技術的な知見、趣味で深めた専門知識、あるいは誰かに伝えたい物語。頭の中にある「伝えたいこと」を一冊の本にまとめ、手に取れる形にする。それは、とても愉しく、やりがいのある営みです。

しかし、いざ書籍を作ろうとすると、執筆以外の作業に多くの時間を取られてしまいます。ページレイアウト、目次や図表番号の管理、索引づくり、表紙の作成、入稿用 PDF の調整……。

**Vivlio Starter** は、そうした作業を引き受け、書き手が「書くこと」に集中できる環境を提供する CLI ツールです。Markdown で書いた原稿から、印刷所に入稿できる PDF と、Kobo / Apple Books / Kindle 向けの電子書籍を生成します。

組版エンジンには CSS 組版の [Vivliostyle](https://vivliostyle.org/) を使っています。`vs build` は二十を超える工程からなり、Vivliostyle が受け持つのは PDF と EPUB の紙面を組む工程です。原稿の前処理（数式・図・索引・相互参照など）と、出力の後処理（表紙の結合・しおり・入稿用 PDF・Kindle 用の変換など）は、Vivlio Starter が担います。

2026 年 11 月に、正式版の **v1.0.0** を公開しました。付属のガイドブック『はじめての技術書づくり』（A4・283 ページ）も Vivlio Starter 自身で組んでいます。

- リポジトリ: https://github.com/Atelier-Mirai/vivlio-starter
- RubyGems: https://rubygems.org/gems/vivlio-starter
- ガイドブック（技術書典）: https://techbookfest.org/product/qMsQg0tjxaYgRjs33zCaPG?productVariantID=m89uTcKPhu08bzpdx1FJHH

## 1 行で始める

macOS では、ターミナルに次の 1 行を入力すると、Homebrew・Ruby・Vivlio Starter・執筆に使うツール一式がインストールされます（15 分ほどかかります）。

```bash
zsh -c "$(curl -fsSL https://raw.githubusercontent.com/Atelier-Mirai/vivlio-starter/master/bin/install.zsh)"
```

続けて次の 3 行で、最初の PDF ができます。

```bash
vs new mybook       # プロジェクト作成
cd mybook
vs build            # PDF を生成（できた PDF を開きます）
```

Ruby 3.4 以上があれば、`gem install vivlio-starter vivlio-starter-pdf` でもインストールできます。不足しているツール（Vivliostyle・ImageMagick・Ghostscript など）は、最初の `vs new` がインストールします。「まず環境構築で半日溶かす」を避けたかったところです。

新しい章を書くときは:

```bash
vs create 10-awesome        # 章ファイルと画像ディレクトリを生成し、catalog.yml に登録
vs build  10-awesome        # その章だけ素早くビルドして確認
```

プロジェクトを作らずに、手元の Markdown 1 枚をそのまま組むこともできます。書き捨てのメモや企画書向けの軽量経路です。

```bash
vs build myawesome.md --theme blue
```

## 執筆ワークフロー

| ステップ | 主なコマンド | 内容 |
| :--- | :--- | :--- |
| ① プロジェクト作成 | `vs new mybook` | 雛形生成＋必要ツール自動セットアップ |
| ② 執筆 | `vs create 10-intro` | 章ファイルを追加して Markdown で執筆 |
| | `vs build 10-intro` | 章単位で素早く確認 |
| ③ 整える | `vs lint` | 文章を校正（textlint） |
| | `vs metrics` | 原稿の分量と読みやすさを確認 |
| | `vs preflight` | ビルド前の原稿エラーを数秒で検出 |
| ④ ビルド | `vs build` | 書籍全体をビルド |
| ⑤ 入稿・配布 | — | 生成済みファイルを提出・アップロード |

②と③は何度でも繰り返せます。書いては整え、また書く——この往復が、読みやすい技術書を仕上げる近道だと思っています。

## 出力先ごとに最適化する

`config/book.yml` の `output.targets` で指定します。カンマ区切りで併記できます。

| 頒布先 | 指定する値 | 生成されるもの |
| :--- | :--- | :--- |
| 技術書典・コミケ（印刷所入稿） | `print_pdf` | トンボ・塗り足し付き PDF（CMYK 表紙は PDF/X-1a） |
| ダウンロード販売・PDF 配布 | `pdf` | 閲覧用 PDF（表紙結合済み） |
| 楽天 Kobo・Apple Books・BOOTH | `epub` | EPUB |
| Amazon Kindle（KDP） | `kindle` | KPF（Kindle Previewer 4 で変換） |

EPUB と Kindle を分けているのには理由があります。Kindle（KFX）は `var()` も `color-mix()` も解釈せず、`::before` の疑似要素ラベルも無視します。同じ EPUB を両方へ出すと、どちらかが必ず妥協することになります。

そこで **EPUB** は WebP・高画質 SVG・テーマ色をそのまま使い、**Kindle 用**にはテーマ色を具体的な色として焼き込み、WebP を JPEG/PNG へ変換し、`::before` のラベルを実体の要素として差し込んだ EPUB を別に組みます。横に広い表は、Kindle では**組んだ PDF のページを画像として差し替え**ます。リフロー型では再現できないレイアウトを、見た目そのままで届けるための割り切りです。

EPUB は epubcheck の ERROR が 0 件であることを、リリースのたびに検査しています。Kindle 向けは、Kindle Previewer 4 の画面で表示を確かめています。

## 書きやすさのための記法

一般的な Markdown に加えて、本を書くときに「あると助かる」記法を足しています。

### 図解注釈 `:::{.showcase}`

スクリーンショットに「ここを見てほしい」という枠・矢印・丸数字を付けたいとき、通常は画像編集ソフトを開くことになります。この記法では、それを**原稿に文字で書きます**。

````markdown
:::{.showcase}
![バイオリンを弾くアインシュタイン](Einstein.webp)
# 行頭が # の行はコメントです（出力されません）
rect:1 530, 335, 175, 165 {pos=bottom} 愛用のバイオリン
pointer:2 490, 130 {label="白髪"} くしゃくしゃの白髪
:::
````

これをビルドすると、次の 1 枚の画像に焼き込まれます。

![図解注釈の出力例](/images/vivlio_starter_introduction/showcase.jpg)

`rect:1` の `1` は丸数字の番号、続く 4 つの数字が位置と大きさです。座標は千分率なので、画像を差し替えてもずれません。元の画像には一切手を加えないので、注釈だけを原稿と一緒にバージョン管理できます。

### 数式は見たまま書ける

`$x² + y² = r²$`・`$√(a+b)$`・`$Σ(i=1 to n) i$` のように、見たままの形で書けば、そのまま数式として組まれます。LaTeX を知らなくても大丈夫です。もちろん LaTeX の記法でも書けます。

数式は MathJax で SVG に焼き込むので、PDF・EPUB・Kindle で同じ見た目になります。Kindle ではインライン数式を本文の文字に落とし、文字サイズの変更に追従させています。

### ダイアグラム ` ```mermaid `

フローチャートやシーケンス図をテキストで描けます。

![mermaid で描いたフローチャート](/images/vivlio_starter_introduction/mermaid.jpg)

PDF はベクタ、EPUB・Kindle はラスターで、すべてのターゲットに同じ図が出ます。図中のフォントは本の見出し書体に自動で揃うので、図だけ書体が浮くことはありません。

### 会話文 `:::{.talk}`

「キー: 発話」を並べるだけで、話者ごとに色分けした吹き出しになります。

![会話文の出力例](/images/vivlio_starter_introduction/talk.jpg)

話者の色・アバター・左右の振り分けは `config/talk.yml` で定義します。上の例のようにアバター画像が無くても、頭文字を白抜きした簡易アバターを自動生成するので、絵ができる前から書き進められます。

### そのほか

- **相互参照** — `@chapref:ch-intro` や `@pageref:fig-flow` と書くと、章番号・図番号・ページ番号はビルド時に決まります。章を並べ替えても番号を手で直す必要はありません
- **拡張テーブル** — セルの横結合（`||`）と複数行ヘッダーが、素のパイプテーブルのまま書けます
- **`@` ディレクティブ** — `@vspace` で余白を微調整、`@pagebreak:recto` で右起こし、`@qr:URL` で QR コード、`@version` / `@today` でビルド時の値を差し込み
- **コードの取り込み** — ` ```include:sample.rb:10-20 ` のように `codes/` から範囲指定で取り込むと、**元ファイルでの実際の行番号**（この例なら 10 から）が表示されます。紙面を見ながら元ファイルの該当箇所を探せます
- **データ展開** — YAML のデータから、書籍紹介カードや表を生成できます

## 上下巻も、全巻の合本も

1.0.0 で、一冊を上下巻に分けて刊行する**分冊**に対応しました。原稿は `contents/` に一つにまとめたまま、`config/catalog.yml` に巻ごとの章の構成を書きます。

```yaml
VOLUMES:
  - name: 上巻               # 各巻の呼び名
    id: upper               # 各巻の識別子（コマンドと出力ファイル名に使う）
    CHAPTERS:
      - 11-intro
      - 12-basics

  - name: 下巻
    id: lower
    CHAPTERS:
      - 21-advanced
      - 22-practice
```

```bash
vs build upper   # 上巻を組む
vs build all     # 全巻を、巻の順に一巻ずつ組む
vs build         # 全巻を一冊にまとめた合本を組む
```

章番号は巻をまたいで続き、別の巻の章や図は「上巻 第8章」のように参照できます。書名・表紙・発行日・ISBN は巻ごとに上書きでき、全巻の構成を示す「全巻目次」も載せられます。

## 執筆を支える道具

### 文章校正 `vs lint`

表記揺れ・冗長な表現・文体の混在を textlint で検出します。英単語の綴りも 50 以上の技術辞書で確認します。

日本語ならではの指摘として、`だ円`（楕円）・`進ちょく`（進捗）のような**交ぜ書き**を約 2,000 語の辞書で拾います。直し方が一つに決まる指摘は、`vs lint --fix` で自動修正できます。

### 分量と読みやすさの分析 `vs metrics`

刊行された技術書の実測（9 冊・104 章・408 節）から定めた基準で、章の分量が適切かを判定します。

工夫したのは、**分量を「本文」で数える**ことです。コードブロックと記法を除いた地の文の量で測ります。コード込みで数えると、コードが多い章ほど「足りている」と判定されてしまうためです。

指摘の記号も使い分けています。分量は 💡（提案）、文章の質は 🤔（気になる点）、理想の帯に収まれば ✅。分量の指摘を 💡 にしているのは、それが欠陥ではなく提案だからです。読解難度は建石式、語彙の多様さは MATTR という定評ある指標を使っています。

### 書く前の点検 `vs preflight`

PDF を組まずに、画像やコードの置き忘れ、未定義の参照、本の書体にない字、組めない数式を数秒で検出します。指摘には、原稿の場所と直し方を添えます。

### 索引・用語集

「索引をどう作ればよいか分からない」という手前で止まってしまう機能だと思うので、そこを解きほぐす方向で作りました。

- `vs index:auto` — 原稿から索引語の候補を抜き出し、レビューファイルにまとめます。著者は印を付けて採否を決め、`vs index:apply` で辞書に登録します
- `vs index:plan` — 索引づくりの**下見**。本文の分量から索引語数の目安を算出し、いまの語数が多いか少ないかを示します。辞書もレビューファイルも書き換えません
- **主要参照** — その語を腰を据えて説明している章を指定すると、索引でそのページが太字＋先頭に並びます。機械が候補を下書きするので、著者は確認するだけで済みます

辞書の説明文や見送った語は、次の本へ引き継げます。

## 今ある原稿から始める

- **`vs pdf:read`** — PDF を読み取り、見出し・表・コードを含む Markdown の章へ変換します。`vivlio-starter-pdf` をインストールすると、画像の取り出しと、スキャンした PDF の OCR もできます
- **`vs import`** — [Re:VIEW Starter](https://kauplan.org/reviewstarter/) のプロジェクトを、Vivlio Starter のプロジェクトへ変換します

`vs import` で難しいのは、Re:VIEW の Markdown 変換器が `//sideimage`（画像の脇に本文を回す）・`//output`（実行結果）・`//clearpage`（改ページ）を**印を残さずに**平坦なテキストへ落とすことです。変換後の Markdown だけを見ても、どこまでが画像の脇に置く本文なのか決められません。

そこで、章ごとに `.re` 原稿を開き直し、**元の構造をそのまま移す**方式にしました。推測しないので、段落が複数あっても箇条書きを含んでいても崩れません。

## 印刷入稿グレードのフォント品質

ここは苦労したので書き残しておきます。

印刷所は **Type 3 フォント**（字形がそのまま PDF に焼き込まれる埋め込み方式）を嫌います。入稿時の事故や文字のにじみの原因になるためです。Vivlio Starter では PDF 内のフォントを**すべて通常の埋め込み・Type 3 ゼロ**に揃え、全章のビルドのたびに検査しています。含まれていれば、ページと字を報告します。

同梱書体だけでなく、**著者が Google Fonts の書体を選んだ場合も 0 件**です。ここで分かったのが、日本語 Google Fonts 55 書体を調べたところ **31 書体が太字を持たない**ということでした。太字を持たない書体に `font-weight: bold` を当てると、Chrome が合成太字（faux-bold）を作り、それが Type 3 化します。

そこで合成太字を止め、本文書体に太字が無いときだけ強調を見出し書体へ振る仕組みを入れました。生成 SVG（図解注釈・mermaid）は独立文書で本文の CSS が届かないため、**その SVG に出る字だけ**を抜き出したフォントを埋め込んでいます（8 文字で 3.3KB）。本の書体に無い字（𝔽 や絵文字など）も、予備の書体や字の形の SVG で補います。

「CSS は正しいのに効かない」たぐいの落とし穴が CSS 組版には多いので、この手の知見はリポジトリの [`docs/specs/`](https://github.com/Atelier-Mirai/vivlio-starter/tree/master/docs/specs) に notes として溜めています。同じところで悩んでいる方の役に立つかもしれません。

## しくみ

Vivliostyle は「HTML + CSS を紙面に組む」ところを担い、その前後を Vivlio Starter が担当します。

### 前処理（Vivliostyle 呼び出し前）

- **QueryStream 展開** — `data/*.yml` のデータを `templates/` のテンプレートで自動展開
- **画像最適化** — 出力ごとの派生を生成（PDF は JPEG・EPUB は WebP）。紙面に対して過剰な解像度は自動で詰めます
- **クロスリファレンス** — 図・表・コードリストへの参照を自動解決
- **ソースコード読み込み** — `codes/` からコードを埋め込み、行番号を付与
- **脚注変換** — 外部リンクをページ脚注に自動変換
- **数式・図の画像化** — MathJax / mermaid / showcase
- **索引スキャン** — 辞書の語を本文から探し、初出とそれ以降を区別してタグ付け
- **CSS 自動更新** — テーマカラー・版面設定を動的生成
- **目次の自動生成** — `catalog.yml` の各章から見出しを抽出

### 後処理（Vivliostyle 呼び出し後）

- **重複バックリンク排除** — 生成済み PDF の named destinations からページマッピングを取得し、索引・用語集の重複リンクを浄化
- **PDF アウトライン付与** — しおり（ブックマーク）を付与
- **表紙 PDF 結合** — frontcover / backcover を本文 PDF と結合
- **奥付の偶数ページ調整** — 奥付が必ず左ページに来るよう空白ページを自動挿入
- **入稿用 PDF の導出** — 閲覧用 PDF の中間成果物からトンボ・塗り足し付きの PDF を作成
- **EPUB / Kindle の生成** — ターゲットごとに最適化した EPUB を組み、Kindle は KPF へ変換

ガイドブック（A4・283 ページ）は、キャッシュを消してから全章ビルドすると約 3 分です（閲覧用 PDF のみ）。内訳は次のとおりで、約 6 割が Vivliostyle が紙面を組む時間です。

```
vivliostyle 本体:      約 61%（107 秒：本文 PDF の組版 53 秒・バックリンク解決の再組版 53 秒）
vivlio-starter の処理: 約 39%（67 秒：テーマ画像の用意 24 秒・原稿の前処理 12 秒・HTML 変換 6 秒・しおり付与 6 秒など）
```

画像や数式の生成結果はキャッシュに残るので、2 回目からのビルドはさらに短くなります。執筆中は `vs preflight`（数秒）と単章ビルドで確認し、仕上げに全章ビルドするのが快適です。

## 設定は 1 ファイルに

`config/book.yml` に集約しています。すべて既定値を持っているので、書かなければ既定で動きます。

```yaml
book:
  main_title: "はじめての技術書づくり"
  subtitle: "Vivlio Starter 実践ガイド"
  author: "早乙女 遙香"

theme:
  style: image      # image: 扉絵あり / simple: 扉絵なし
  color: green      # アクセントカラー（12 色 ＋ HEX 指定）

page:
  use: b5_standard  # 判型と版面のプリセット

output:
  targets: pdf      # pdf / print_pdf / epub / kindle（併記可）
```

判型は A5 / B5 / A4 それぞれに標準・広め・狭め・カスタムのプリセットがあります。章の改丁（`chapter_pagebreak`）や、節をページ先頭から始めるか（`section_pagebreak`）も選べます。既定の右起こしは製本らしい体裁になりますが、章の変わり目に白紙が入ります。ページ単価で刷る同人誌では `any` が効きます。

設定の説明と今の値は `vs config:book` で確かめられます。gem を更新したら `vs upgrade` を一度実行すると、本体・プロジェクトの雛形・外部ツールをまとめて更新し、`book.yml` の新しいキーと廃止されたキーも整理します。原稿・画像・辞書は上書きしません。

## 動作要件

- **Ruby 3.4 以上**（3.4.12 と 4.0.9 で動作確認）
- **Node.js 22.12 以上**（Vivliostyle CLI 11 系の要件）
- macOS + Homebrew 環境を主対象としています（外部ツールの自動導入はこの環境でのみ動作します）
- Kindle 向けの出力には Kindle Previewer 4 が必要です

## おわりに

Vivlio Starter の開発は、[Re:VIEW Starter](https://kauplan.org/reviewstarter/) に触発されたことに始まります。Re:VIEW Starter が示した「執筆者が執筆に集中できる環境づくり」という思想は、Vivlio Starter の根幹にあり続けています。作者の kauplan さんに厚く御礼申し上げます。

また、コアエンジンである [Vivliostyle](https://vivliostyle.org/) の作者・開発チームの皆様にも深く感謝申し上げます。CSS 組版という優れた技術と、オープンソースとしての惜しみない公開があってこそ、Vivlio Starter は生まれました。

開発を始めてから 1 年 3 か月、何度も公開を延ばしながら改良を重ね、ようやく正式版にたどり着きました。`vs new` でプロジェクトを作り、`vs build` で PDF を生成する——その瞬間のワクワク感を、あなたにも味わっていただけたら嬉しく思います。

**さあ、あなたの本を書きましょう！**
