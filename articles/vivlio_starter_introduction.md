## はじめに

「自分の本を作ってみたい」——そう思ったことはありませんか。

日々の仕事で培った技術的な知見、趣味で深めた専門知識、あるいは誰かに伝えたい物語。頭の中にある「伝えたいこと」を一冊の本にまとめ、手に取れる形にする。それは、とても愉しく、やりがいのある営みです。

しかし、いざ書籍を作ろうとすると、執筆以外の作業に多くの時間を取られてしまいます。ページレイアウト、目次の生成、画像の配置、表紙の作成、入稿用 PDF の調整……。

**Vivlio Starter** は、そうした煩雑な作業をすべて引き受け、書き手が「書くこと」に集中できる環境を提供する CLI ツールです。Markdown で書いた原稿から、印刷所に入稿できる PDF と、Kobo / Apple Books / Kindle 向けの電子書籍を生成します。

CSS 組版エンジン [Vivliostyle](https://vivliostyle.org/) をコアに据えていますが、単なるラッパーではありません。原稿の前処理から目次生成、索引の構築、表紙作成、トンボ付き入稿用 PDF の出力まで、必要な処理の約半分を独自に担っています。

この記事を書いている時点で **v1.0.0-rc.2** です。付属のガイドブック『はじめての技術書づくり』（A4・347 ページ）も Vivlio Starter 自身で組んでいます。

- リポジトリ: https://github.com/Atelier-Mirai/vivlio-starter
- RubyGems: https://rubygems.org/gems/vivlio-starter

## 3 コマンドで本ができる

```bash
gem install vivlio-starter --pre   # 現在はリリース候補版のため --pre が要ります

vs new mybook       # プロジェクト作成（必要な外部ツールも自動セットアップ）
cd mybook
vs build            # PDF を生成
vs open             # 生成された PDF を開く
```

`vs new` は内部で `vs doctor --fix` を呼び、Vivliostyle・ImageMagick・Ghostscript など必要な外部ツールを一括で導入します。「まず環境構築で half day 溶かす」を避けたかったところです。

新しい章を書くときは:

```bash
vs create 10-awesome        # 章ファイルと画像ディレクトリを生成
vs build  10-awesome        # その章だけ素早くビルドして確認
```

プロジェクトを作らずに、手元の Markdown 1 枚をそのまま組むこともできます。書き捨てのメモや企画書向けの軽量経路です。

```bash
vs build myawesome.md --theme blue
```

## 執筆ワークフロー

| ステップ | 主なコマンド | 内容 |
| :--- | :--- | :--- |
| ① プロジェクト作成 | `vs new mybook` | 雛形生成＋必要ツール自動セットアップ |
| ② 執筆 | `vs create 10-intro` | 章ファイルを追加して Markdown で執筆 |
| | `vs build 10-intro` | 章単位で素早く確認 |
| ③ 整える | `vs lint` | 文章を校正（textlint） |
| | `vs metrics` | 原稿の分量と読みやすさを確認 |
| | `vs preflight` | ビルド前の原稿エラーを数秒で検出 |
| ④ ビルド | `vs build` | 書籍全体をビルド |
| ⑤ 入稿・配布 | — | 生成済みファイルを提出・アップロード |

②と③は何度でも繰り返せます。書いては整え、また書く——この往復が、読みやすい技術書を仕上げる近道だと思っています。

## 出力先ごとに最適化する

`config/book.yml` の `output.targets` で指定します。カンマ区切りで併記できます。

| 頒布先 | 指定する値 | 生成されるもの |
| :--- | :--- | :--- |
| 技術書典・コミケ（印刷所入稿） | `print_pdf` | トンボ・塗り足し付き PDF（CMYK 表紙は PDF/X-1a） |
| ダウンロード販売・PDF 配布 | `pdf` | 閲覧用 PDF（表紙結合済み） |
| 楽天 Kobo・Apple Books・BOOTH | `epub` | クリーン EPUB |
| Amazon Kindle（KDP） | `kindle` | KPF（Kindle Previewer 経由で自動変換） |

EPUB と Kindle を分けているのには理由があります。Kindle（KFX）は `var()` も `color-mix()` も解釈せず、`::before` の疑似要素ラベルも無視します。同じ EPUB を両方へ出すと、どちらかが必ず妥協することになります。

そこで **クリーン EPUB** は WebP・高画質 SVG・テーマ色をそのまま維持し、**Kindle 用**にはテーマ色を具体色として焼き込み、WebP を JPEG/PNG へ変換し、`::before` ラベルを実体の要素として注入した中間 EPUB を別に組みます。横に広い表は、Kindle では**組んだ PDF ページを画像として差し替え**ます。リフロー型では再現できないレイアウトを、見た目そのままで届けるための割り切りです。

クリーン EPUB・Kindle 中間 EPUB のどちらも **epubcheck の ERROR 0 / WARNING 0** を通しています。

## 書きやすさのための記法

一般的な Markdown に加えて、本を書くときに「あると助かる」記法を足しています。

### 図解注釈 `:::{.showcase}`

スクリーンショットに「ここを見てほしい」という枠・矢印・丸数字を付けたいとき、通常は画像編集ソフトを開くことになります。この記法では、それを**原稿に文字で書きます**。

````markdown
:::{.showcase}
![バイオリンを弾くアインシュタイン](Einstein.webp)
# 行頭が # の行はコメントです（出力されません）
rect:1 530, 335, 175, 165 {pos=bottom} 愛用のバイオリン
pointer:2 490, 130 {label="白髪"} くしゃくしゃの白髪
:::
````

`rect:1` の `1` は丸数字の番号、続く 4 つの数字が位置と大きさです。座標は千分率なので、画像を差し替えてもずれません。元の画像には一切手を加えないので、注釈だけを原稿と一緒にバージョン管理できます。

### ダイアグラム ` ```mermaid `

フローチャートやシーケンス図をテキストで描けます。PDF はベクタ、EPUB・Kindle はラスターで、すべてのターゲットに同じ図が出ます。

### 会話文 `:::{.talk}`

「キー: 発話」を並べるだけで、話者ごとに色分けした吹き出しになります。話者の色・アバター・左右の振り分けは `config/talk.yml` で定義します。アバター画像が無くても、頭文字を白抜きした簡易アバターを自動生成します。

### そのほか

- **拡張テーブル** — セルの横結合（`||`）と複数行ヘッダーが、素のパイプテーブルのまま書けます
- **`@` ディレクティブ** — `@vspace` で余白を微調整、`@pagebreak:recto` で右起こし、`@qr:URL` で QR コード、`@version` / `@today` でビルド時の値を差し込み
- **コードの取り込み** — ` ```include:sample.rb:10-20 ` のように `codes/` から範囲指定で取り込むと、**元ファイルでの実際の行番号**（この例なら 10 から）が表示されます。紙面を見ながら元ファイルの該当箇所を探せます
- **数式** — LaTeX 記法を MathJax で SVG へ焼き込み。PDF・EPUB・Kindle で同じ見た目になります

## 執筆を支える道具

### 文章校正 `vs lint`

表記揺れ・冗長表現・文体の混在を textlint で検出します。英単語の綴りも 50 以上の技術辞書で確認します。

### 分量と読みやすさの分析 `vs metrics`

刊行書の実測（章 128 件・節 408 件）に基づく基準で、章の分量が適切かを判定します。

工夫したのは、**分量を「本文」で数える**ことです。コードブロックと記法を除いた地の文の量で測ります。コード込みで数えると、コードが多い章ほど「足りている」と判定されてしまうためです。

指摘の記号も使い分けています。分量は 💡（提案）、文章の質は 🤔（気になる点）、理想の帯に収まれば ✅。分量の指摘を 💡 にしているのは、それが欠陥ではなく提案だからです。

`--all` を付けると、章間のばらつき、見直したい長い文、文末表現のリズム、よく使う言葉、漢字レベル（ルビ候補）まで出します。読解難度は建石式、語彙多様度は MATTR という定評ある指標を使っています。

### 索引・用語集

「索引をどう作ればよいか分からない」という手前で止まってしまう機能だと思うので、そこを解きほぐす方向で作りました。

- `vs index:plan` — 索引づくりの**下見**。本文の分量から索引語数の目安を算出し、いまの語数が多いか少ないかを示します。辞書もレビューファイルも書き換えません
- 採否は**スコアの閾値ではなく「目安語数の帯」**で決めます。「スコア 300 以上を採用」のような閾値は、本の分量で意味が変わってしまうためです
- **主要参照** — その語を腰を据えて説明している章を指定すると、索引でそのページが太字＋先頭に並びます。機械が候補を下書きするので、著者は確認するだけで済みます

## 印刷入稿グレードのフォント品質

ここは苦労したので書き残しておきます。

印刷所は **Type 3 フォント**（字形がそのまま PDF に焼き込まれる埋め込み方式）を嫌います。入稿時の事故や文字のにじみの原因になるためです。Vivlio Starter では PDF 内のフォントを**すべて通常の埋め込み・Type 3 ゼロ**に揃えています。

同梱書体だけでなく、**著者が Google Fonts の書体を選んだ場合も 0 件**です。ここで分かったのが、日本語 Google Fonts 55 書体を調べたところ **31 書体が太字を持たない**ということでした。太字を持たない書体に `font-weight: bold` を当てると、Chrome が合成太字（faux-bold）を作り、それが Type 3 化します。

そこで合成太字を止め、本文書体に太字が無いときだけ強調を見出し書体へ振る仕組みを入れました。生成 SVG（図解注釈・mermaid）は独立文書で本文の CSS が届かないため、**その SVG に出る字だけ**を抜き出したフォントを埋め込んでいます（8 文字で 3.3KB）。

「CSS は正しいのに効かない」たぐいの落とし穴が CSS 組版には多いので、この手の知見はリポジトリの [`docs/specs/`](https://github.com/Atelier-Mirai/vivlio-starter/tree/master/docs/specs) に notes として溜めています。同じところで悩んでいる方の役に立つかもしれません。

## しくみ

Vivliostyle は「HTML + CSS を紙面に組む」ところを担い、その前後を Vivlio Starter が担当します。

### 前処理（Vivliostyle 呼び出し前）

- **QueryStream 展開** — `data/*.yml` のデータを `templates/` のテンプレートで自動展開
- **画像最適化** — WebP 変換・リサイズ
- **クロスリファレンス** — 図・表・コードリストへの参照を自動解決
- **ソースコード読み込み** — `codes/` からコードを埋め込み、行番号を付与
- **脚注変換** — 外部リンクをページ脚注に自動変換
- **数式・図の画像化** — MathJax / mermaid / showcase
- **索引スキャン** — 辞書の語を本文から探し、初出とそれ以降を区別してタグ付け
- **CSS 自動更新** — テーマカラー・版面設定を動的生成
- **目次の自動生成** — `catalog.yml` の各章から見出しを抽出

### 後処理（Vivliostyle 呼び出し後）

- **重複バックリンク排除** — 生成済み PDF の named destinations からページマッピングを取得し、索引・用語集の重複リンクを浄化
- **PDF アウトライン付与** — しおり（ブックマーク）を付与
- **表紙 PDF 結合** — frontcover / backcover を本文 PDF と結合
- **奥付の偶数ページ調整** — 奥付が必ず左ページに来るよう空白ページを自動挿入
- **入稿用 PDF の導出** — 閲覧用 PDF の中間成果物からトンボ・塗り足し付きの PDF を作成
- **EPUB / Kindle の生成** — ターゲットごとに最適化した EPUB を組み、Kindle は KPF へ変換

ビルド時間の内訳はおおむね次のとおりで、大半は Vivliostyle が紙面を組む時間です。

```
vivliostyle 本体:      約 85%（本文 PDF の組版・バックリンク解決の再組版）
vivlio-starter の処理: 約 15%（前処理・後処理・PDF 結合・しおり付与）
```

執筆中は `vs preflight`（数秒）と単章ビルド（約 30 秒）で確認し、仕上げに全章ビルドするのが快適です。

## 設定は 1 ファイルに

`config/book.yml` に集約しています。すべて既定値を持っているので、書かなければ既定で動きます。

```yaml
book:
  main_title: "はじめての技術書づくり"
  subtitle: "Vivlio Starter 実践ガイド"
  author: "早乙女 遙香"

theme:
  style: image      # image: 扉絵あり / simple: 扉絵なし
  color: green      # アクセントカラー（12 色 ＋ HEX 指定）

page:
  use: b5_standard  # 判型と版面のプリセット

output:
  targets: pdf      # pdf / print_pdf / epub / kindle（併記可）
```

判型は A5 / B5 / A4 それぞれに標準・広め・狭め・カスタムのプリセットがあります。章の改丁（`chapter_pagebreak`）や、節をページ先頭から始めるか（`section_pagebreak`）も選べます。既定の右起こしは製本らしい体裁になりますが、章の変わり目に白紙が入ります（ガイドブックでは全体の約 5%）。ページ単価で刷る同人誌では `any` が効きます。

## Re:VIEW Starter からの引っ越し

`vs import` で既存の [Re:VIEW Starter](https://kauplan.org/reviewstarter/) プロジェクトを取り込めます。

ここで難しいのは、Re:VIEW の Markdown 変換器が `//sideimage`（画像の脇に本文を回す）・`//output`（実行結果）・`//clearpage`（改ページ）を**印を残さずに**平坦なテキストへ落とすことです。変換後の Markdown だけを見ても、どこまでが画像の脇に置く本文なのか決められません。

そこで、章ごとに `.re` 原稿を開き直し、**元の構造をそのまま移す**方式にしました。推測しないので、段落が複数あっても箇条書きを含んでいても崩れません。

## 動作要件

- **Ruby 3.4 以上**（3.4.10 と 4.0.6 で動作確認）
- **Node.js / npm**（Vivliostyle CLI や textlint に必要）
- macOS + Homebrew 環境を主対象としています（外部ツールの自動導入はこの環境でのみ動作します）
